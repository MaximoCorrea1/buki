# Design: Book Catcher (working name)

Catch books from Twitter before they get lost.

Generated by /office-hours (ultra-powers) on 2026-07-20
Mode: Builder (real but chill)
Status: APPROVED
Owner: Maximo (@MaxoCorrea)

## Problem Statement

Maximo reads a lot (math, engineering, and more) and constantly finds books
recommended on Twitter/X, usually as a cover photo in a post. He saves them
meaning to read them later. Capture is not the problem. Two things break:

1. Saved books get buried in the pile, mixed with memes, threads, and random bookmarks.
2. He can't tell the books he's serious about from impulse saves ("someday maybe" vs "I really want this one").

Result: the books he meant to read get lost and forgotten. This is a *place*
problem and a *priority* problem, not a save-button problem.

## What Makes This Cool

- One tap on a tweet turns a cover photo into a real, structured book in your
  own reading list, with title, author, and cover resolved automatically.
- Every save keeps **why** you wanted it: the tweet that sold you is stored with
  the book, so when you come back you see the context, not a cold title.
- The list is intent-aware (Now / Next / Someday), so the ones you mean it about
  never blur into the pile.
- It resurfaces the right book at the right moment so you actually read it,
  instead of hoarding a dead list.

## Constraints

- Solo builder, first product, wants craft. The build must be realistic for one person.
- Browser extension on Twitter/X (Manifest V3).
- Own the reading list as source of truth (decided this session). Export/sync is a bonus.
- Keep cost near zero for a hobby launch.

## Premises (agreed this session)

1. The real job is organization + intent, not capture. (Maximo: the break is "buried in the pile" plus "can't tell the serious ones.")
2. Recognition is a cheap, solved problem, not the moat. The moat is taste plus the anti-forgetting UX.
3. This is a narrow, opinionated wedge for book-Twitter / STEM readers, not a mass-market app.
4. Own the list. Goodreads is a dead end as a write target (API closed since 2020, old keys erroring by 2025). CSV/OpenLibrary export is the bridge.

## Key Research Findings

- **Prior art:** No tool recognizes a book inside a tweet and one-click saves it
  to a reading list. Closest: "Add Book to Goodreads" (retail pages only),
  "TBR Bookmarker" (page text only, ~dead at 27 users). Genuine gap, shallow moat:
  the pieces exist separately, assembling them in the feed is the new part.
- **Recognition (feasible and cheap):** Send the tweet's image + text to a
  low-cost vision model (Gemini 2.5 Flash-Lite, ~$0.0002/lookup) for
  {title, author, confidence, alternates}, then verify against Google Books /
  OpenLibrary to get canonical title/cover/ISBN and kill hallucinations. Show a
  1-3 candidate confirm step. As an extension, read the tweet from the DOM
  (data-testid selectors) and skip the now-paid X API entirely.
- **Write targets (2026):** Goodreads = CSV import only (no API). StoryGraph =
  no API. Hardcover = good API but forbids browser use, no OAuth yet
  (server-side only). OpenLibrary = best client-side fit (open, writes via
  session cookie). Google Books = stable OAuth but legacy/low-use. Plan: own the
  list; OpenLibrary sync first; Google Books via OAuth second; Hardcover
  server-side later; Goodreads-format CSV as the universal export (imports into
  both Goodreads and StoryGraph).
- **Demand:** Real but narrow. Strong, recurring pain among tech/STEM readers and
  book-Twitter (lost recs, the bookmark black hole, "Goodreads is broken," TBR
  guilt). Power users pay ~$10/mo (Readwise, Fable, StoryGraph Plus); casual
  readers expect free. Reads as a sharp freemium wedge, not a mass category.
  Caveat: Reddit was inaccessible to the researcher, so the general-reader signal
  is lighter than ideal.

## Recognition: verified findings (2026-07-21)

Empirically checked with a real Tesseract.js run + live grounding, not just unit tests:

- **Free OCR reads clean covers "OK-ish."** It reliably reads clear typography
  (technical titles, subtitles, author names; SICP came back clean) but mangles large
  stylized display titles ("Clean Code" -> "yo: EB"). Per-cover confidence ran 47-73%.
  These were flat cover SCANS; real tweet photos (angled, hands, glare) will be worse.
  Tune against real tweets, not clean scans.
- **Grounding (OpenLibrary) is excellent on clean queries.** Even a partial signal
  grounds correctly: the OCR'd *subtitle + author* of Clean Code ("A Handbook of Agile
  Software Craftsmanship Robert C. Martin") resolved to Clean Code. Google Books works
  too but is keyless-rate-limited (hit a live 429); OpenLibrary has no hard quota, so
  prefer it as the primary grounding source.
- **The lever is query hygiene, not better OCR.** Dumping the whole noisy OCR blob as
  the query fails - garbage tokens like "Eton Tm iT" break the match.
- **Per-word OCR confidence is not exposed** by tesseract.js v6 here (`data.words` and
  the `blocks:true` word tree both came back empty), so confidence-filtering isn't a
  free option.
- **Robust approach = "let grounding be the filter":** try candidate strings (OCR
  lines / the tweet text / the raw guess) against the books DB and keep whichever
  resolves to a real book, instead of guessing which line is the title. Single-line
  heuristics (first-line, longest-line) each fail on some covers.
- **Verdict:** the $0 path (Tesseract + OpenLibrary + confirm step) is viable for "OK,"
  carried by the text/link pre-checks on the easy cases. Keep Gemini Flash-Lite as a
  one-line `VisionClient` swap for the covers OCR mangles.

## Review pass (2026-07-23) — what changed

A 9-persona review before first browser run found 3 P0s and 12 P1s, all in the browser
glue layer (the recognizer core came through clean). Fixed:

- **Silent data loss (P0).** `storage.add()` was an unlocked read-modify-write; two
  overlapping saves dropped one book while toasting success for both — reproduced live.
  All writes now serialize through a promise queue. Never write to the storage key
  outside `createLibrary`.
- **Unrecoverable wrong saves (P0).** The OCR flow auto-saved the first fuzzy match with
  no relevance check, and nothing could delete it. Added: a match must share a
  significant word with the query, entries carry an id, `remove()` exists, and the popup
  has a delete button. Auto-save is kept deliberately — it is the flow's whole point.
- **Invisible operation (P0).** The context menu appeared on every image on every site,
  but the toast content script only exists on x.com — so off-Twitter the pipeline ran
  and mutated the shelf with zero feedback. Menu is now scoped via `documentUrlPatterns`
  and `host_permissions` narrowed from `<all_urls>` to the five hosts actually used.
  *To broaden beyond Twitter later, add a `chrome.notifications` feedback channel first.*
- **Signature feature was broken.** `info.pageUrl` is the tab's URL, not the tweet's, so
  every right-click save recorded `x.com/home`. The background worker now asks the
  content script to resolve the permalink from the image, and provenance is stored as
  `{url, kind: 'tweet' | 'page'}` so the popup can label it honestly.
- **Reliability:** `getWorker()` resets on failure (a rejected promise is truthy, so one
  transient error disabled OCR for the whole session); `ensureOffscreen()` shares one
  in-flight promise; the 150ms readiness guess became a real ping/ack handshake; all
  network calls carry `AbortSignal.timeout`; `res.ok` is checked before `.json()`; errors
  are staged so a lookup failure no longer blames OCR.
- **Query blowup:** OCR queries capped at `MAX_QUERIES` (was unbounded — a dense image
  could fire 50-100+ sequential requests).
- **UI races:** button `disabled` guards (the old `textContent`-as-state could stick the
  button on `…` forever), single-picker enforcement with one cleanup path, toast
  stacking, and a rAF-coalesced observer scoped to `main[role="main"]` plus an interval
  safety net for in-place node recycling.
- **Security:** retailer-host allowlist before trusting a scraped `/dp/` link, truncated
  link text dropped, `http(s)`-only source links.
- **Removed as unreachable:** `ocrVision.ts`, `tesseractOcr.ts` (a trap — no path
  overrides, would have fetched from a CDN and failed CSP), `googleBooks.ts`.
- **Build:** dropped 3 unreachable non-LSTM Tesseract cores (54MB -> 30MB), `tsc` chained
  into `build`, `noUncheckedIndexedAccess` on, icons generated, repo initialized.

Still open: the 4 extension entry points have no automated tests (chrome glue; covered
by the manual pass instead), and CSV export is unbuilt.

## First-run bug: OCR worker refused to load (2026-07-23)

**Symptom.** Right-click → "Save book to shelf" always ended in "Couldn't read that
image." Service worker console:
`Failed to execute 'importScripts' on 'WorkerGlobalScope': The script at
'chrome-extension://<id>/dist/tesseract/worker.min.js' failed to load.`

**Root cause.** tesseract.js defaults `workerBlobURL: true`. With that set,
`spawnWorker.js` builds a Blob whose entire body is
`importScripts("<workerPath>")` and runs the worker from a `blob:` URL. A blob worker
has an opaque origin, so Chrome refuses the cross-origin import of a
`chrome-extension://` script and the worker never initializes. The asset was present
and the path was correct — the *loading strategy* was wrong.

**Fix.** Pass `workerBlobURL: false`, taking spawnWorker's other branch
(`new Worker(workerPath)`), which is same-origin with the offscreen document.
**Do not remove that option** — the failure it prevents looks like a missing file.

**Ruled out along the way** (recorded so nobody re-investigates): OpenLibrary CORS is
fine (`access-control-allow-origin: *`), the worker/core/traineddata assets are all
present after the LSTM-only build filter, and the option merge is
`{...defaultOptions, ..._options}` so the override genuinely wins.

## Approaches Considered

### Approach A: Weekend MVP (local, yours only) [CHOSEN]

MV3 extension, no server. Save affordance on each tweet, vision recognize,
tap-to-confirm, save to a local list. Forced Now/Next/Someday intent on every
save. Side-panel list grouped by intent and subject. CSV export. BYOK vision key
(or text-first, image when a key is set). Local storage (IndexedDB).
Effort: S/M. Risk: Low.

### Approach B: The real product (proxy + sync + shelf)

Thin serverless backend proxies the vision call (hides the key, enables a free
tier), syncs across devices, does OAuth for Google Books / session for
OpenLibrary. Full "Spines" shelf, resurfacing, one-click sync-out, freemium.
Effort: L. Risk: Med. This is where A grows.

### Approach C: The anti-forgetting bet (lateral)

Lead with resurfacing: keep the tweet that sold you, and a "your shelf" new-tab
that surfaces one Now book plus why you saved it. Bet the product on the
emotional wedge. Effort: M on top of A. Risk: Med/High.

## Recommended Approach

**A, with C's signature baked in, architected toward B.**

Ship the weekend MVP on your own feed this week. Include the one cheap, unique
thing (store the tweet that sold you plus a gentle resurface) as the signature,
because it is the actual differentiator and costs almost nothing. Model the
storage so it can sync to a backend later (Approach B) once daily use proves it
is worth it. You are solo, it is your first product, and you are the first user.
The fastest read on "is this real" is you living in it for two weeks, not
building infra first.

## Build Order (Next Steps)

1. **Recognizer spike (half a day):** given a tweet's image URL + text, return
   {title, author, cover, confidence}. Vision call then Google Books/OpenLibrary
   verify. Test on 10 real book-tweets from your feed. De-risk the scary part first.
2. **Content script + Save affordance:** inject a button on tweets, scrape
   image/text via data-testid, wire to the recognizer.
3. **Confirm UI:** show 1-3 candidate covers, tap to pick or "type it."
4. **Intent + store:** on save, force Now/Next/Someday; persist to IndexedDB with
   the tweet URL/text attached.
5. **List view (side panel):** grouped by intent, then subject; each book shows
   its cover plus the tweet that sold you.
6. **Signature resurface:** a small "start this one" nudge (new-tab or
   side-panel top) that surfaces one Now book with its context.
7. **CSV export:** Goodreads-format (Title, Author, ISBN, Shelf).

## Success Criteria

- You use it on your own feed for 2 weeks without falling back to bookmarks.
- It catches a book you would otherwise have forgotten, and you actually start reading one.
- Saving feels like a reflex, not a chore: under ~5 seconds, mostly one tap.

## Open Questions / Risks

- **BYOK key security:** an MV3 extension cannot truly hide an API key (storage is
  extractable). Fine for a personal MVP with your own key. For any public release,
  move the vision call behind a proxy (the A to B step).
- **Multiple books in one image (stacks/shelves):** recognizer should return an
  array; confirm UI should allow multi-select. MVP can start single-book and
  degrade to "type it."
- **X DOM fragility:** lean on data-testid, keep a manual "paste tweet URL/text"
  fallback so a layout change does not kill the feature.
- **Google Books rate limit (~1k/day/key):** cache by ISBN/work; consider
  OpenLibrary as primary metadata source (no hard quota).
- **Cold start:** your list is empty on day one; the resurface feature only bites
  once you have saved a handful.
- **Naming:** "Book Catcher" is a placeholder.

## Distribution Plan

- Dev: load unpacked in Chrome.
- Later: Chrome Web Store (and Edge). Firefox is a stretch (MV3 differences).
- Not needed for the personal MVP; add it when you want other people using it.

## The Assignment (do this before writing code)

Spend 20 minutes scrolling your own Twitter and collect the next **10 book-tweets**
you would want to catch. For each, note two things: (1) could you name the book
from the *image alone*, and (2) was the title/author in the tweet *text*? This
gives you a real test set for the recognizer, and the image-vs-text ratio tells
you how hard to lean on vision versus just parsing text. Twenty minutes that saves
you a day of guessing.
